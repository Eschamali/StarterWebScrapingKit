=== ANALYSIS REQUEST (for AI) ===
Using ONLY the data in this log, produce four things for THIS site:

1) Network config suggestions
   - IGNORE (bidi.AddIdleIgnoreNetworkPattern): background telemetry / high-freq APIs that
     should NOT gate the SPA idle wait. IGNORE is non-destructive (the request still fires),
     so it is the safe default for first-party telemetry (e.g. /log, generate_204, autocomplete).
   - BLOCK (bidi.ExecuteEnableResourceBlocking): ONLY requests safe to kill (third-party
     ads/analytics/trackers, or bulk resources not needed). BLOCK is page-altering. NEVER block
     hosts that also serve app code/content (e.g. a CDN serving the page's JS), auth/SSO
     endpoints, or anything page logic depends on. If unsure -> IGNORE, not BLOCK.
   - Derive patterns from URLs ACTUALLY seen below (do not guess). '*' = wildcard "contains";
     no '*' = literal substring. Do not over-broaden (use "/log?" literal, NOT "*/log*", which
     would also match /login). Match what was observed (e.g. generate_204, not gen_204).
     Timeline [REQ]/[RES] normalized keys preserve query parameter names but strip values (except
     rpcids and operation-name action values), so patterns such as year= can be derived without
     exposing the original query value.
     [SUPPRESSED] intentionally aggregates more coarsely by normalized host+path plus query presence
     only; use [REQ]/[RES] when query parameter names matter for a suggested pattern.

2) Wait-time assessment
   - Consensus uses current network-idle + DOM-quiet>=minStableMs AND a poll-based
     stable-window timer. stableWindowMs begins at the first sampled poll that satisfies the
     combined condition after WAIT-BEGIN or after any false poll / explicit reset; unsampled
     time never contributes to the confirmation window. Explicit resets include
     dom/vis HIT; net HIT at the first poll that observes it, not its event timestamp;
     probe READY/RECOVERED; navigation reset; probe missing/unhealthy detection.
     Because the true threshold crossing occurs between polls, stableWindowMs is NOT an exact
     post-threshold dwell time or a safety margin. Its amount above minStableMs is largely
     polling phase/overshoot. Do NOT rank or tune waits from that difference.
   - Probe health is fail-safe. Every SPA stability evaluation requires a freshly verified healthy
     probe sample; navigation/unsampled periods contribute NO stability evidence. INITIALIZING/READY
     is normal first-use/new-document setup. UNHEALTHY/RECOVERED is reserved for a probe already
     verified healthy in the same document. READY/RECOVERED restart the full confirmation window.
     At WAIT-END, probeHealthy=true is required for a trustworthy STABLE; otherwise flag error-state.
   - detectedUnhealthyMs starts at the first OBSERVED unhealthy sample, not at the unknown instant the
     probe may actually have disappeared. probeInitializations/probeRecoveries are diagnostics, not
     failures by themselves. Do not infer total probe-absence duration from detectedUnhealthyMs.
   - Check elapsedMs vs maxTimeoutMs (headroom). Any TIMEOUT/HALT = wait too short or a real stall.
   - Discovery recording keeps GLOBAL network.responseCompleted subscribed through navigation URL-stability.
     Use [REQ-UNPAIRED] open-at-end/other to classify remaining unmatched request hops.
   - Long elapsed caused by slow server responses is NOT a threshold problem; do not raise
     minStableMs for that. Infer server latency from the timestamp gaps between consecutive
     [RES]/[NAV] lines (per-request dur is not recorded; see LEGEND).
   - Gated waits ([SPA-WAIT-BEGIN] carries signal=): a TIMEOUT with signal=..:miss is NOT a
     threshold problem -- do not suggest raising minStableMs for it; fix the armed selector/
     pattern or the action instead. For vis HITs, quietAtHit is measured at poll time. For
     net HITs, quietAtHit=unknown by design: lastPolledQuietMs/sampleAgeMs are stale-sample
     diagnostics only and MUST NOT be used to infer a settle-to-render gap. If a
     [SPA-NET-TO-CONTENT] line exists, delayMs=min..max bounds the delay from response completion
     to the first content mutation; relation=INDETERMINATE means the order itself is not determinable.
     observedMs is only the later poll-observation delay and may be much larger when polling or
     recorder-queue work is delayed. A delayMs max near/above minStableMs is a warning/uncertain
     zone, not proof of early completion. Prefer a stable content/visibility gate or a larger
     per-action minStableMs when capture correctness matters. For dom HITs, quietAtHit is
     structurally near zero because the hit itself is a mutation.

3) Settle-to-render suspicion check (early-STABLE warning; the tool pre-computes this)
   - The tool already emits these advisory markers; you do NOT re-derive them by pairing:
     [SPA-CONSENSUS-SUSPECT] = this wait hit STABLE while a tracked json/API it saw produced
       no content render -> treat that STABLE as possibly premature (NOT clean for capture).
     [SPA-CONSENSUS-UNRESOLVED] = the render order could not be determined from the network
       completion interval (INDETERMINATE) or observation window (UNOBSERVED); not a suspect.
     [SPA-CARRYOVER-NOTE] = the immediately next wait in the same browsing context then showed a content render that MAY be
       the previous action's delayed paint. It is a heads-up, not an attribution.
   - Deliberately NOT provided: an exact OWNER-ATTRIBUTED settle-to-render gap or a pairing
     proving which json produced which render. Network completion is an interval, not a point:
     [SPA-NET-TO-CONTENT] gives a delay range for an explicitly armed net signal, and
     owner=not-asserted remains important.
   - The check is adjacent-wait only: a hint lives for exactly ONE following wait, so a SUSPECT
     with no NOTE in the very next wait is not chased further. Absence of a NOTE is not 'safe'.
   - Absence of [SPA-CONSENSUS-SUSPECT] does NOT prove render safety, especially when the relevant
     json/API response or net HIT occurred before SPA-WAIT-BEGIN. BODY STORE presence proves capture,
     not response-to-render timing; do not use BODY ordering in this saved log as temporal proof.
   - Before treating a SUSPECT firstJson as render-producing work, check whether it looks like
     telemetry/beacon/browser-metadata traffic. If so, prefer an IGNORE suggestion for that
     observed endpoint; idle=skip responses do not create SUSPECT state.
   - For an app/content API SUSPECT/NOTE (do NOT just raise minStableMs on an ungated wait):
     re-run with an explicit gate from observed lines to confirm and to get the real timing --
       bidi.ArmContentSignal "<a stable, value-identifying xpath informed by [SPA-ACT]>"
       and/or bidi.ArmNetworkSignal "<substring of the SUSPECT's firstJson key>".
     [SPA-ACT] is sampled/coalesced rather than exhaustive; avoid dynamic IDs when the log
     shows them changing across otherwise similar UI states. Prefer stable attributes.
     With net+content armed, the HITs provide cleaner action-scoped evidence than ungated inference,
     but they still do NOT prove that a specific network response caused a specific render.
     Fallback: on a net-armed wait with no stable DOM selector, an observed
     NET-TO-CONTENT delayMs max near/above minStableMs can justify a more conservative per-action
     minStableMs, but include poll uncertainty rather than treating observedMs as exact.
   - Beware a stale render tripping a naive gate: arming a bare content xpath can HIT on the
     PREVIOUS action's late paint. Prefer a value-identifying selector for the expected content.

Per-line features to use: id (same id across a redirect chain), key (normalized endpoint),
idle (skip|track), [SPA-ACT] (sampled/coalesced DOM mutation evidence), [SUPPRESSED] (filtered-noise tally aggregated by normalized host+path plus query presence; each key carries idle=skip|track).
Exact-value rule for automation code: normalized URL key= entries such as name= may have had their values stripped; [NAV] fragments are redacted, and valueLen= is not input text.
Use [NAV-TARGET] when present for the caller-supplied navigation URL. For any missing URL values, fragments, or typed input text, ASK THE USER; do not silently omit, substitute, or infer them.
If BODY STORE is present, correlate RESPONSE to [RES] and REQUEST to [REQ] by the same ShortId + key. Treat [BODY-SKIP]/[BODY-MISS] as capture outcomes, not evidence that the HTTP body was empty. With default patterns, child-frame/cross-site/unknown-scope JSON is intentionally skipped; explicit body patterns are an opt-in allow-list override.
For multiplexed POST endpoints that reuse the same normalized key, one captured BODY is only one call sample. If additional calls are [BODY-SKIP] reason=cap or unselected, do NOT assume they used the same operation, payload, or response semantics.
A BODY with normalized=True is a canonical AI-oriented representation, not byte-for-byte raw. Small framed bodies below losslessSourceMaxChars are normalized without lossy sampling (compacted=False). compacted=True means some detail may be summarized/sampled; <LONG_STRING len=N>, __ai_omitted_items, and __ai_omitted_members explicitly mark that loss. __ai_envelope__=json-frames marks normalized XSSI/length-framed JSON, and __ai_embedded_json__ marks a JSON string expanded structurally; do not infer omitted values.
Use [BODY-STATS] as the quick outcome summary before inspecting individual BODY records.

4) Reconstruct manual actions from [USER-ACTION] as unverified hints
   - Use element/ancestor/child/shadowHost attributes and visible text as locator candidates; verify against the live DOM and beware hidden duplicates.
   - An id that looks generated (UUID-like, long hex, or long digit runs) may change on every page load; prefer visible text or stable attributes for such elements.
   - Recorded clicks are real (trusted) mouse clicks, but ExecuteClick defaults to a synthetic element.click(). If a replayed click does not produce the change the recording shows after its CONFIRM ([SPA-ACT]/[NAV]), set bidi.UseTrustedClick = True for that click.
   - href/src in [USER-ACTION] are resolved and sanitized, not literal DOM attributes. Never build an exact @href XPath from them; prefer ancestor IDs, visible text, or a distinctive path segment verified against the live DOM.
