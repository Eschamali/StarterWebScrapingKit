## 開発したきっかけ

かつて、Windows と Excel を愛する開発者の手元には、1本の魔法の杖がありました。

```vb
Dim objIE As InternetExplorer

'IE(InternetExplorer)のオブジェクトを作成する
Set objIE = CreateObject("InternetExplorer.Application")

'IE(InternetExplorer)を表示する
objIE.Visible = True

'指定したURLのページを表示する
objIE.Navigate "http://www.vba-ie.net/"
```

たった数行で、外部ライブラリも環境構築も要らず、ブラウザが立ち上がった、そんな時代がありました。  
IE のサポート終了は、その**何も準備しない**手軽さを丸ごと奪っていきました。

現在主流の`SeleniumVBA`も**行数**だけで見ればそこまで差はありません。

```vb
Dim driver As WebDriver: Set driver = New WebDriver
With driver

  '開始する
  .StartChrome

  'ブラウザの起動時の設定(Chrome/Edge兼用)
  Dim caps As WebCapabilities: Set caps = .CreateCapabilities

  '開く
  .OpenBrowser caps

  'サイトを開く
  .NavigateTo "https://note.com/sele_chan/n/n61a67c4379de"
End With
```

起動前設定という概念があるとは言え、拘りがなければそんなに差はありません。  
私も初めはそれを受け入れました。

しかし利用者は受け入れても、裏には以下のような概念が付きまとうことになります🫠

- WebDriver運用/管理(一応、SeleniumVBAはこの辺の管理はやってくれる🙂)
- 社内通信環境
- セキュリティポリシー

![ASRアラート](/img/story/human/6.png)

等と言った実際に動かさないと気付かないような問題が露になりました。  

> 「あの頃の、インストール不要でブラウザを意のままに操れる手軽さを、現代の**AI技術**でなんとか復活させることはできないだろうか🥲」

そんな思いで、2025年年末に開発をスタートしました😶

いまでこそ「Excel VBA 単体で CDP と WebDriver BiDi を喋るコアエンジン」などと名乗っていますが、最初のコミットに詰まっていたのは、正直に言えば **他人のライブラリの寄せ集め** でした。

## 受信ロジックの最適化1

オリジナルの[受信ロジック](https://github.com/longvh211/Chromium-Automation-with-CDP-for-VBA/blob/main/Class%20Modules/CDPBrowser.cls#L1436)を拝見すると、こういうのを見つけました

![オリジナルの受信ロジック](/img/story/human/10.png)

`strBuffer = strBuffer & strRes`

こういうのが要所要所ちりばめられています。VBAにちょっと詳しい方ならご存じ、この書き方では処理速度の低下につながってしまう書き方です。

VBAの文字列は「後ろに空きスペース」を持っていません。そのため `&` で結合するたびに、裏では以下のような「引っ越し作業」が発生しています。

1. **新しい土地を探す：** 「元の文字数 ＋ 追加する文字数」が収まる**新しいメモリ領域**を確保する
2. **荷物を全部運ぶ：** 今までの `strBuffer` の内容を、新しい場所に**まるごと全コピー**する
3. **新しい荷物を置く：** 追加分の `strRes` を後ろにくっつける
4. **元の家を解体する：** 古い `strBuffer` のメモリを破棄する

データが小さいうちは一瞬ですが、受信ループが何十回・何百回と回り、バッファが大きくなればなるほど**「毎回、巨大なデータを丸ごと新しい場所にコピーし直す」**ことになります。

受信データが雪だるま式に増えるにつれてコピーにかかる時間も二次関数的に激増し、最終的に「処理がフリーズしたように遅くなる」という現象を引き起こします。

こういったパフォーマンス低下を防ぐべくこのバージョンは色々とテコ入れしました。  
そのせいでオリジナルでは起こらなかった問題が、意図せず次々と発生しては修正...を繰り返す日々が続きました。

時間はかかりましたが、この時点での結論は、`Split(A, vbNullChar)` で一気に[配列にバラして裁く手法](https://github.com/Eschamali/StarterWebScrapingKit/blob/c2ee72e9c843534f9b6bc0686d5faa01e936498d/VBAProject/Class/CDPCore.cls#L869)でした。

![Split方式受信ロジック](/img/story/human/11.png)

「よし、これで遅い結合地獄からは抜け出せた！」
ひとまず実用的な速度を手に入れ、戦いは終わったかのように見えました。

……しかし、これは後に訪れる「真の最適化」へと至る、長大な物語のプロローグに過ぎませんでした。
巨大パケットという怪物を前に、この設計すら過去のものとなる「第2形態」への覚醒は、もう少し先のお話です——。

## JavaScriptの実行方法を豊富に

この頃になるとロジックフローや、CDP知識そのものに対する理解度は、当初とは比べ物にならないほど深くなっていました🤠

これまでのバージョンアップは、言うなれば「便利な機能の継ぎ足し」でした。本家ライブラリの偉大な面影（土台）を保ちつつ、周りに飾り付けをしているような状態です。  
しかし、低レイヤの仕様が頭に入ってきた今、改めてこれまでのコアコードを見つめ直すと、本家ライブラリの「とりあえず動くようにしただけ」の簡素な記述が、どうしても目立ち、気になり始めました🫪

>「もっとCDP本来の、圧倒的な潜在能力を解き放てるはずだ🤠」

まず着手したのが、自動化の勝敗を分ける最重要機能、JavaScript（Runtime.evaluate / functionDeclaration）の実行オプションの拡張でした。

最近のReactやVueなどのSPA（シングルページアプリケーション）が支配するモダンなWebサイトにおいて、ブラウザの内部状況に最も精通しているのは、やはりJavaScript自身です。
そのため、CDPの仕様書には、JavaScriptを実行するためのAPIに膨大な「制御用パラメータ」が用意されていました。

![Runtime.evaluateで扱えるmethod一覧](/img/story/human/15.png)

しかし、本家の実装は、ただ「JavaScriptのコード（文字列）」を1つ送るだけの、非常にシンプルな設計になっていました。これでは宝の持ち腐れです🥺

![オリジナルライブラリの実装状況](/img/story/human/16.png)

私はCDPのドキュメントを貪り読み、実務で絶対に役立つ強力なパラメータを片っ端からピックアップし、すべて実装コードに叩き込みました。

- objectId：特定のDOM要素などのオブジェクトを直接基準にしてJavaScriptを実行する
- objectArguments：objectId の関数に対して、VBA側から引数を安全に引き渡す
- returnByValue：True にすることで、JavaScriptが返してきた複雑なオブジェクトを、VBA側でパース可能な具体的な「値（JSON構造）」として受け取れる。
- awaitPromise：True にすると、JavaScript内の非同期処理（Promiseの解決など）が終わるまでVBA側を待機させ、最終的な結果をスマートに同期的に受け取れる。
- userGesture：True にすることで、そのJS実行を「人間が手動でクリックやキーボード操作を行った結果」であるとChromeに偽装して認識させる。
- allowUnsafeEvalBlockedByCSP：True にすると、Webサイト側がCSP（コンテンツセキュリティポリシー）で外部スクリプトの実行をガチガチに禁止している環境であっても、それを完全に無視してすべてのJavaScriptの実行を強制許可する。
- これらをすべて満載したため、VBAのメソッドの引数定義は、改行マーク（, _）がこれでもかと並ぶ凄まじい弾幕のようなシグネチャになりました😂

![数行の引数](/img/story/human/17.png)

これにより、戻ってきたデータが数値だろうが、テキストだろうが、あるいはパースされたDictionaryやCollectionであっても、シームレスにVBA側で受け取れるようにしたのです。

万が一、JavaScriptの実行中にエラー（例外）が発生した場合、VBAの標準エラー値オブジェクトである CVErr(xlErrValue) を返して即座にエラーを報告させ、別途用意したプロパティに例外のスタックトレースの詳細をきれいに記録する仕組みを構築しました。VBAが持つ「Variantの柔軟性」と「エラー値オブジェクト」という、泥臭くも強力な足腰（言語仕様）をフルに引き出した設計です。

![エラー判定部分](/img/story/human/18.png)

これで、どんな高度なJavaScript操作もVBAから自由自在に実行できる、無敵のJS実行環境が完成しました🤠

## `CDPElement` を作り直す

コア刷新の波は、ツール全体の最大の長所である「要素（Element）操作クラス」にも及びました。

[本家ライブラリ](https://github.com/longvh211/Chromium-Automation-with-CDP-for-VBA/blob/main/Class%20Modules/CDPElement.cls)には、XPathなどで検索した要素を基準にしてクリックや入力をしたり、さらにその要素の下層にある子要素を検索したりする、非常にありがたい要素操作用の「Classオブジェクト（Elementクラス）」がすでに備わっていました。

しかし、その「検索した要素（Element）」の保持方法に、CDPを深く理解した今だからこそ、どうしても許せないまどろっこしさがありました。

本家は、取得した要素(例：[ID要素](https://github.com/longvh211/Chromium-Automation-with-CDP-for-VBA/blob/main/Class%20Modules/CDPBrowser.cls#L771))を以下のように管理していたのです。

```vb
Public Function getElementByID(strID As String) As CDPElement
   'Get a new unique varID
    Dim varID As String: varID = newVarID	' ランダムな文字列

   'Get the object and assign to the varID in the browser
    Dim varJS As String: Dim result As String
    varJS = varID & " = document.getElementById(""" & strID & """)"	'VBA側で一時的なランダムな変数名を生成し、グローバル（window）に保存させていた
    result = jsEval(varJS)

   'Return result
    Set getElementByID = New CDPElement
    getElementByID.init Me, varIDs, varID, varJS, result

End Function

Private Function newVarID() As String
    Dim newID As String

   'Init the ID collection
    If varIDs Is Nothing Then Set varIDs = New Scripting.Dictionary

    Do: newID = "varID" & Format(Rnd * 100000, "000000")
    Loop Until Not varIDs.Exists(newID)
    varIDs.Add newID, newID

   'Return the new varID
    newVarID = newID

End Function
```

ブラウザ側のグローバル空間（window）に、VBA側がランダムな変数名を勝手に生やして要素を代入し、VBA側のDictionaryでその変数名を管理する。
当初は動けばいいと思っていましたが、CDPに精通した今となっては、あまりにも不格好で、不自然なアプローチに思えました🙃

さらに、この 「`window`グローバル空間に、不自然なグローバル変数が大量に生成されていく挙動」 は、近年高度化しているセキュリティ・スクレイピング検知システム（ボット検知）にとって、「一発でプログラムによる自動操作だと見破られて、通信を遮断（ブロック）される」という最大のリスクでもありました🫠

「本物のブラウザ自動操作は、window を1文字も汚すことなく、ブラウザの裏側のメモリだけで静かに行われるべきだ🤠」

解決策は明確でした。CDPが[標準](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#type-RemoteObject)で提供している objectId 方式に、要素管理のすべてを移行することです 。
![Runtime.evaluateのObjectID](/img/story/human/19.png)

要素を取得した際、Chromeが内部メモリで管理している一意のオブジェクト識別子（objectId）を受け取り、VBA側はそのIDだけを静かに保持して操作を指示する。

やることはシンプルですが変更行は割とあります🫠  
こういうときこそAIです😳

> 「この要素操作クラスの変数管理システムを、本家のインターフェース（使いやすさ）は変えずに、内部をすべてCDP標準の`objectId`方式に美しく移管して、リファクタリングして」

### VBA用Jsonパーサーの世代交代

通信コアを `WithEvents` でスマートにしたのに、パケットの中身を解析する最深部が、**8年以上更新の止まっていた VBA-JSON**を使ってます。この`VBA-JSON`...

- 存在するKeyとValueを全部、Dictionary/CollectionにコピーしてVBAとして扱いやすくする

というロジックです。一般的なRestWebAPIなら、このロジックでも問題ありません。でもCDPはそうはいきません。  
特にイベント情報を扱うとなると下手したら毎秒何百件も来るのもざらにあります😵  
もっと言うと、全部が欲しいわけではないはずです。特定の値さえ取れればそれで十分というのがほとんどです。全部欲しいのは精々ログ表示程度です。

にも拘らず、この`VBA-JSON`は、全部コピーしてしまう🫥でも、VBAでJsonを扱うライブラリはこれしか選択肢名がなく、じゃ～`VBA-JSON`そのものをいじるとなるとまた頭がおかしくなりそうです😵

偶然なのか必然なのか、そんなタイミングでピッタリなJsonパーサーライブラリが登場しました🥳

**[vbacollective-json](https://github.com/vbacollective/json)**

ちょっと難しい解説ですが、  
このJsonパーサー、**JSON 文字列のメモリに `SAFEARRAY` を直接かぶせて、部分文字列を一切コピーせずに読む**（ゼロコピー）という方式を使ってます。パース中に `Dictionary` も `Collection` も生成しません。CDP のレスポンスは 大量に来がちなので、ここが効きます。

ただしこのJsonパーサーは、読み取り専用です。`v1.1.0`で実装した、イベント情報をDictionaryに蓄積では、このライブラリは相性が悪いです。  
が、これもすぐに解決できました。というか、`VBA-JSON`の上位互換がありました🤠

**[VBA-FastJSON](https://github.com/cristianbuse/VBA-FastJSON)**

一応、読み取りも書き出しも両対応ですが、読み取りに関しては、`vbacollective-json`が圧倒的に早いです。  
よって、読み取りと書き出しを分けるような仕組みになりました。

`vbacollective-json`は基本的に、結果を受け取るだけのポジションになりました。

そして、VBAでJsonを扱う際のあの儀式もこのライブラリによって消え去ってくれました🥹

### 生ソケットへの逆襲

AIとディスカッションを続けたらこんなワードをくれました。

**WinSock**

実態は「Pipeにネットワークの送受信を足した、ただそれだけの土管」。ここで私は、WebSocketの真の仕様をようやく理解しました。

**WebSocketという専用の魔法のパイプが通っているのではない。**  
ただの生ソケット（TCPという土管）の上に、RFC 6455というルールに沿って**「決められた規格の封筒（フレーム）にデータを詰め、ちょっと目隠し（マスク）をして流しているだけ」**だったのです。

---

#### 💡 そもそも[RFC 6455](https://www.rfc-editor.org/info/rfc6455/)の正体ってなんなの？（3つのルール）

1. **フレーム構築（荷札貼り）：**
   「このメッセージはテキストだよ」「長さは○○バイトだよ」「これで終わりだよ（FIN）」という**ヘッダー（荷札）**を先頭にくっつけて、ただの文字列を「1つの小包」に仕立てる作業。
2. **マスクXOR（目隠し）：**
   暗号化（秘密を守る）ではなく、途中の通信機器（プロキシ）が「ん？これ普通のHTTP通信か？」と勘違いしてキャッシュ事故を起こさないよう、**ランダムな4バイトの数字でデータをパラパラと撹乱（モザイク処理）しているだけ**。
3. **断片化（複数個口での発送）：**
   巨大なデータが来たら、「1箱目（続きあり）」「2箱目（これで最後）」と小分けにして土管に流すルール。

---

これをAIに教わり、気づきました。

> そうか、Microsoftが用意した専用API(WinHttpWebSocketReceive等)がなくても、**WinSockで生データを送受信できる土管さえ用意して、この『荷造り（ビット演算）』と『開封作業』をVBAで手書きしてやれば、WebSocketなんて自作できるじゃん！！**」

こうして、PowerShellも使わない、「VBA × 生WinSockによるWebSocket自作」という道が開かれたのです。

### 通信経路の拡張はどうしたの？

さて、せっかくCDP via WebSocket のコアClassを出来上がったのに、これをどう拡張するのか🤔  
実はもう答えは頭に浮かんでます。

`RaiseEvent`です。

v2.0.0実装前は全然イメージが付けなかったこの`RaiseEvent`、もう今となっては仕組みを理解済みです。

```vb
'ストリームに書き込み、イベント発信
WebSocketReceiveStream.Write payloadBuffer
RaiseEvent WebSocketReceive(payloadBuffer, TakePayloadSize, AllPayloadReceive And m_WebSocketFrame.isFIN)
```

▲ 受信した内容をイベント発信し...

```vb
Private Sub viaWebSocket_WebSocketReceive(res() As Byte, resSize As Long, EOS As Boolean)
    Const FromProcedureName As String = ThisClassName & ".viaWebSocket_WebSocketReceive"


    'ストリームに流し込む ※バッファー拡張は、`ADODB.Stream`が担います
    CDPPipeStream.Write res
    printMsg Trace_, "Storing received messages...", FromProcedureName

    'メッセージの終わりであれば、その目印も追記
    If EOS Then CDPPipeStream.Write m_NullTerminator

    '取得サイズをcursor管理へ反映し、バッファー拡張判定を行う
    StrBufferCheck resSize + EOS * -1
    printMsg Trace_, "ResSize = " & resSize & " , EOS: " & EOS, FromProcedureName
End Sub
```

▲ コアでイベントを受け取る！

そして、またしてもこの`ADODB.Stream`の恩恵を受けたのです😳

```txt
【--remote-debugging-pipe】   ───> (そのままアペンド) ─────────────────┐
                                                                     │ ──> 【ADODB.Stream】 ──> (一括UTF-8変換) ──> (Midステートメントによる高速カーソル処理)
【--remote-debugging-port】   ───> (IsFIN(EOS)なら、末尾に0x00を付加) ─┘
```

1. Pipe版のデータを受信した場合：
そのまま ADODB.Stream に Write で流し込んで蓄積する。
2. Port版（WebSocket）のデータを受信した場合：
ヘッダーサイズをパースし、メッセージの終わりであることを確認後、コッソリと vbNullChar（0x00） をその場でドッキングさせてから、ADODB.Stream に Write で流し込んで蓄積する。
3. 共通の後続処理：
両者のパケットが溜まった ADODB.Stream から、一括でUTF-8テキストに超高速変換。変換後のテキストに対し、VBAが誇る伝家の宝刀 Mid ステートメントを使って高速にカーソル（cursor）操作を走らせ、vbNullChar を区切り文字として1件ずつ安全にパースして取り出す。
「Port版のデータを、その場で『Pipe版のフォーマット（末尾Null文字）』に翻訳してストリームに流し込む」🤠

このハックを思いついたことで、私は複雑なWebSocket専用の難解な受信パースロジックを新規に書き加えることなく、既存の高速なPipe受信フローと 「ほぼ完全なコピペレベルの一元化（共通化）」 に成功したのです🥳🫨

AIと対談しながら、ミリ秒のカーソル（cursor）管理のデバッグに手こずり、泥臭く調整を重ねた末、ついに「Port」と「Pipe」が完全に合流した、最強の受信エンジンが稼働可能な状態に整いました🥳

これが[v2.3.0](https://github.com/Eschamali/StarterWebScrapingKit/releases/tag/v2.3.0)の登場です。

## 将来の拡張に備えて

`v2.0.0`で磨き上げた、`TakeEvents`  
受信からイベント発火までを一手に引き受けるメソッドでした。それを 3 つに割りました。

| メソッド | 責務 |
| --- | --- |

```vb
    ' ついでに新しく届いた分も取り込む
    If viaWebSocket Is Nothing Then TakePipe ... Else TakeWebSocket ...
    Call ReadyCDPMessage

```

分割後は、こうなります。

```vb

AnalyzeCDP StopApiError, destruction
```

## こうして登場した1枚のマクロブック

こうして今、1枚のマクロブックが登場しました😳
![1枚のマクロブック](/img/story/human/1.png)

よくある業務効率ツール？ いいえ  
社員から直してと言われたマクロ？ いいえ  
便利機能を寄せ集めたもの？ そうかも  

このマクロには、かつて存在した**「1行の魔法」**が込められています。

```bas
Sub sample()

　Dim objIE As Object

　' IE(InternetExplorer)のオブジェクトを作成する
　Set objIE = CreateObject("InternetExplorer.Application")
　objIE.Visible = True

End Sub
```

IEの消滅とともに失われた、あの「Excelからブラウザを直接操る魔法」。  
**それを、令和の「Chrome / Edge」として蘇らせました。**

```bas
Sub sample()

　Dim objChrome As Object

　' Chrome（またはEdge）のオブジェクトを作成する
　Set objChrome = Priset.StartBrowser

End Sub
```

![2種類のブラウザ](/img/story/human/2.png)


**外部ツールのインストールは一切不要**  
もう一度言います。

WebDriverも、アドインも、PowerShellファイル配置等、面倒な設定もいりません。  
このExcelファイルを開くだけで、あなたの目の前でChrome/Edgeが動き出します。  
あ、管理者権限もいりませんよ🤠
